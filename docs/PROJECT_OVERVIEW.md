# EdgeShield AI — Project Overview

**Privacy-preserving, explainable, edge-deployable AI intrusion detection for IoT networks, trained federatedly on CICIoT2023.**

---

## 1. What this project is

EdgeShield AI is a complete, working intrusion-detection system (IDS) for IoT networks.
A compact neural network watches every network flow coming from IoT devices (cameras,
industrial sensors, routers, medical monitors, smart-home hubs) and classifies it in
real time as **Normal** or one of five attack families — **DDoS, Brute Force, Scanning,
Spoofing, Malware** — using the 46-feature CICIoT2023 flow schema.

What makes it different from a typical "ML model in a notebook" project:

- The model is **small enough to run on the device/gateway itself** (75.3 KB, int8-quantized
  ONNX, 54,470 parameters, 0.026 ms mean inference on one CPU thread).
- It is **trained without pooling anyone's raw data** — federated learning (FedAvg,
  5 non-IID clients), so only model weights ever leave a device.
- Every detection is **explained** — per-flow SHAP attributions show *which features*
  made the model raise the alarm.
- Everything is visible in a **real-time SOC dashboard** (React + Socket.IO): live threat
  feed, per-flow explanations, federated-training replay, measured edge benchmarks,
  and a network map.

The demo is fully offline and deterministic (seed 42): a one-click scenario replays five
attack waves against a simulated 5-device fleet, and **every verdict on screen is a real
inference of the trained model** — nothing is scripted or faked. Simulated traffic is
clearly labeled as such in the UI.

## 2. What we are doing (the pipeline)

```
CICIoT2023 dataset (263,064 real flows after cleaning)
        │  preprocess.py — clean, scale, encode, stratified split (provenance recorded)
        ▼
EdgeShieldNet (MLP 46→256→128→64→6, ~55k params)
        │  train.py — GPU training (85 epochs, RTX 4080, ~200 s)
        │  run_federated.py — the same net trained with FedAvg across 5 non-IID clients
        ▼
int8 post-training quantization (quantize.py → ONNX)
        │
        ▼
ml-inference-service (FastAPI): /predict · /explain (SHAP) · /model-info
        │
        ▼
backend (Node + Socket.IO, deterministic scenario engine) → React SOC dashboard
```

**Measured results** (held-out test set of 39,460 flows, generated by
`benchmarks/compare_baseline.py` — see `docs/results.md`):

| Metric | Centralized IEEE-style baseline | EdgeShield AI |
|---|---|---|
| Accuracy | 0.8600 | 0.8515 (int8) |
| F1 (macro) | 0.8298 | 0.8205 |
| Model size | 1,661 KB (fp32) | **75.3 KB (int8) — 22.1× smaller** |
| Parameters | 422,150 | 54,470 |
| Latency (mean / p95) | 0.048 / 0.058 ms | **0.026 / 0.028 ms — 1.8× faster** |
| Raw data leaves device | Yes | **No (weights only)** |
| Explainable | No | **Yes (SHAP per flow)** |
| Runs on edge hardware | No | **Yes** |

Federated training reaches **83.84% global accuracy** in 10 FedAvg rounds vs the 85.30%
centralized reference — i.e. we give up ~1.5 points of accuracy to gain full data privacy,
and the trade-off is measured, not assumed.

## 3. Why it matters (impact)

- **Privacy / compliance.** Hospitals, factories, and smart buildings often *cannot
  legally ship raw traffic* (patient telemetry, production data) to a cloud for training.
  Federated training means the IDS improves collectively while raw flows never leave the
  premises — this unlocks IDS deployment in exactly the sectors most attacked today.
- **Cost and latency.** A 75 KB model classifying a flow in 0.026 ms runs on
  router/gateway-class hardware. No GPU server, no cloud round-trip, no bandwidth bill
  for shipping traffic mirrors — detection happens where the attack lands.
- **Trust and triage.** A SOC operator can't act on a black-box "trust me, it's malware."
  Per-flow SHAP shows *why* (e.g. Protocol Type, Header_Length, inter-arrival time drove
  the verdict), turning an alert into something a human can verify, triage, and defend to
  a regulator.
- **Resilience.** No central inference server means no single point of failure and no
  single high-value target; each edge node keeps defending even if disconnected.
- **Honest evaluation culture.** Every number in the UI cites its source artifact; nothing
  is fabricated. As a research/demo methodology, this is itself a contribution — judges
  and reviewers can trace any claim to the script that produced it.

## 4. Specialty — what we add over the previous IEEE-style work

Published IEEE ML-IDS papers on IoT (including the CICIoT2023 reference models) almost
universally share the same architecture: pool all raw traffic on a server, train a large
float32 model, report accuracy, stop. Our baseline (`BaselineNet`, 422k params) is a
faithful reproduction of that recipe, and we beat it on every *operational* dimension
while staying within ~1 point of its accuracy:

| # | Gap in the IEEE-style approach | EdgeShield's answer | Proof in this repo |
|---|---|---|---|
| 1 | **Centralized inference** — traffic must travel to a server | On-device int8 ONNX inference | `ml-inference-service/`, latency measured per request |
| 2 | **Server-class model** — too heavy for gateways | 22.1× smaller model, 1.8× faster, quantization cost measured (85.30% → 85.15%) | `ml-engine/quantize.py`, `benchmarks/results.json` |
| 3 | **Raw data pooling** — privacy is surrendered by design | FedAvg across 5 non-IID device shards; only weights move | `federated-learning/run_federated.py`, real per-round curve in `history.json` |
| 4 | **Black-box verdicts** — no reasoning offered | SHAP (Expected Gradients) per class *and* per individual flow, live | `ml-inference-service/explain/`, `/explain` endpoint |
| 5 | **Results live in notebooks** — no operational surface | Real-time SOC dashboard driven only by live inference events | `backend/` + `frontend/` |

Two methodological specialties on top:

- **Like-for-like comparison.** Baseline and EdgeShield are trained on the same data,
  same split, same machine, and evaluated on the same held-out test set — the comparison
  table is generated by one script on the demo machine, not copied from papers.
- **Non-IID federated realism.** Each simulated client's shard is skewed toward its own
  device profile (60% one attack class), matching how real deployments see data — and the
  cost of that heterogeneity is visible in the convergence curve rather than hidden by an
  unrealistic IID split.
